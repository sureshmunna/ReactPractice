DAY 1

useState — Stale Closures, Batching, Lazy Init

The #1 hook, and the #1 interview trap

1. Stale Closures

A function inside useEffect captures a variable's value at creation time and never sees updates, because the effect doesn't re-run. 
// ❌ BUGGY — count is frozen at 0 forever
useEffect(() => {
  const timer = setInterval(() => {
    setCount(count + 1) // always reads count = 0
  }, 1000)
  return () => clearInterval(timer)
}, [])

// ✅ FIXED — functional update gets the LATEST value from React
useEffect(() => {
  const timer = setInterval(() => {
    setCount(c => c + 1) // always fresh
  }, 1000)
  return () => clearInterval(timer)
}, [])

2. React 18 Batching

Multiple setState calls — even inside async functions — are batched into ONE re-render in React 18. 
const handleClick = async () => {
  await fetch('/api')
  setCount(c => c + 1)  // batched
  setName("Suresh")      // batched — only 1 render total
}

3. Lazy Initialisation

// ❌ Runs expensiveCalc() on EVERY render
const [value, setValue] = useState(expensiveCalc())

// ✅ Runs ONLY ONCE on mount — pass a function, not a value
const [value, setValue] = useState(() => expensiveCalc())
Interview Answer

"A stale closure happens when a function captures a variable's value at creation time and never sees updates. The fix is functional updates like setState(prev => prev + 1), so React always hands back the latest value directly instead of reading a frozen variable."

DAY 2

useEffect — Cleanup, Race Conditions, When NOT to Use It

The most misunderstood hook in React

1. Three situations where you should NOT use useEffect

  • Deriving state — just calculate directly: const fullName = first + " " + last
  • Filtering/transforming data — filter inline: const active = users.filter(u => u.active)
  • Responding to user events — handle it in the event handler, not in an effect watching state

2. Race Conditions — AbortController

Two fetches firing (e.g. user clicks quickly) can resolve out of order — the older, slower one can overwrite the newer result. 
useEffect(() => {
  const controller = new AbortController()

  fetch(`/api/user/${userId}`, { signal: controller.signal })
    .then(res => res.json())
    .then(data => setUser(data))
    .catch(err => {
      if (err.name === "AbortError") return // cancelled — ignore
    })

  return () => controller.abort() // cancel previous fetch on change
}, [userId])

3. Cleanup Function

Runs before the next effect execution AND on unmount. Prevents memory leaks — cancel timers, abort fetches, remove listeners.
Interview Answer

"useEffect is only for synchronising with external systems — APIs, timers, subscriptions. If I'm just deriving or filtering data, I calculate it directly during render instead of syncing it into state via an effect."

DAY 3

useMemo, useCallback, React.memo

Reference equality — the root of unnecessary re-renders

Reference Equality

// Primitives — compared by VALUE
1 === 1              // ✅ true

// Objects/Arrays/Functions — compared by REFERENCE
{} === {}              // ❌ false — different memory addresses

useMemo — cache a VALUE

const user = useMemo(() => ({ name }), [name])
// same reference unless 'name' changes → child with memo() skips re-render

useCallback — cache a FUNCTION

const handleDelete = useCallback((task) => {
  setTasks(prev => prev.filter(t => t !== task))
}, [])
// stable function reference → memo() on child TaskItem actually works
Can useMemo make things SLOWER? Yes — it has its own cost (storing + comparing dependencies). Only use it for genuinely expensive calculations or stable references for child components.
Interview Answer

"useMemo caches a computed value; useCallback caches a function reference. Both exist to prevent child components wrapped in memo from re-rendering just because they received a new object/function reference every render, even when the actual data hasn't changed."

DAY 4

useReducer

Complex state, never mutate directly

Never Mutate State

// ❌ Mutating — React won't detect the change (same reference)
case "update":
  state.name = "Suresh"
  return state

// ✅ Return a NEW object — React sees a new reference, re-renders
case "update":
  return { ...state, name: "Suresh" }

useReducer vs useState

  • useState → simple, independent values
  • useReducer → multiple related sub-values, complex transitions, many action types
Interview Answer

"React uses reference equality to detect state changes. Mutating an object directly keeps the same reference, so React thinks nothing changed and skips the re-render. Always return a new object with spread syntax."

DAY 5

Context Performance Splitting

Why one combined context causes unnecessary re-renders
When state and dispatch live in ONE context, every consumer re-renders on ANY change — even components that only use dispatch, which React guarantees never changes. 
// ✅ Split into two contexts
const AppStateContext = createContext(null)
const AppDispatchContext = createContext(null)

// dispatch-only components NEVER re-render on state change
const TaskInput = memo(() => {
  const dispatch = useAppDispatch() // only subscribes to dispatch
  ...
})
Interview Answer

"Splitting state and dispatch into separate contexts means dispatch-only consumers never re-render, since dispatch is guaranteed stable by React. Combined with memo, this gives fine-grained control without any external library."

DAY 6

Custom Hooks

useFetch, useDebounce, useLocalStorage — built from scratch

useDebounce

const useDebounce = (value, delay) => {
  const [debounced, setDebounced] = useState(value)
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay)
    return () => clearTimeout(timer) // cancel if value changes before delay
  }, [value, delay])
  return debounced
}

useLocalStorage

const useLocalStorage = (key, initialValue) => {
  const [value, setValue] = useState(() => {
    const item = localStorage.getItem(key)
    return item ? JSON.parse(item) : initialValue
  })
  const setAndStore = (v) => {
    setValue(v)
    localStorage.setItem(key, JSON.stringify(v))
  }
  return [value, setAndStore]
}
Interview Answer

"Custom hooks are functions starting with 'use' that encapsulate reusable stateful logic. I create one when the same combination of hooks repeats across multiple components — it makes code DRY and testable."

DAY 7

Zustand

Global state, no Provider, automatic selective re-rendering
const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set(state => ({ count: state.count + 1 })),
}))

// component only re-renders when 'count' changes — nothing else
const count = useCounterStore(state => state.count)

Zustand vs Context vs Redux

  • Context — free, built-in, needs manual splitting for performance
  • Zustand — tiny, no Provider, automatic selective re-rendering
  • Redux — powerful, heavy boilerplate, best for huge enterprise apps
Interview Answer

"Zustand needs no Provider and gives automatic selective re-rendering — components only re-render when their specific subscribed slice of state changes. Context requires manually splitting state/dispatch to get the same effect."

DAY 8

React Query (TanStack)

Server state — caching, dedup, background refetch, all built in
const { data, isLoading, error } = useQuery({
  queryKey: ["users"],
  queryFn: fetchUsers,
  staleTime: 1000 * 60, // fresh for 1 minute
})

const mutation = useMutation({
  mutationFn: addTask,
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ["tasks"] })
})

Client State vs Server State

  • Client state (theme, form inputs) → useState / Zustand
  • Server state (users, tasks from API) → React Query
Interview Answer

"useEffect fetching has no caching, no dedup, no retry, and manual loading states. React Query solves all of this — it caches by queryKey, dedupes identical requests, retries on failure, and refetches stale data in the background automatically."

DAY 9

Concurrent React

useTransition, useDeferredValue, Suspense

useTransition

const [isPending, startTransition] = useTransition()

setInput(e.target.value)          // urgent — instant
startTransition(() => {
  setSearch(e.target.value)       // non-urgent — can be delayed
})

useDeferredValue

const deferredSearch = useDeferredValue(search)
// input stays instantly responsive; heavy list catches up when React has time

Suspense + lazy()

const LazyCard = lazy(() => import('./HeavyComponent'))

<Suspense fallback={<p>Loading...</p>}>
  <LazyCard />
</Suspense>
Interview Answer

"useTransition marks state updates as non-urgent — React prioritises input responsiveness first, then processes the transition when it has time. useDeferredValue achieves something similar but for a value you already have, useful when you can't access the setState directly."

DAY 10

Interview Q&A Recap

The questions most likely to come up
  • Virtual DOM? — Lightweight JS copy of real DOM; React diffs old vs new tree, updates only what changed.
  • Stale closure fix? — Functional updates: setState(prev => ...)
  • When NOT to use useEffect? — Deriving state, filtering data, responding to events.
  • useMemo vs useCallback? — Value vs function reference caching.
  • Why never mutate state? — React uses reference equality to detect changes.
  • Context performance fix? — Split state and dispatch into separate contexts.
  • Zustand vs Context? — No Provider, automatic selective re-rendering.
  • Why React Query over useEffect? — Caching, dedup, retry, background refetch, built-in loading/error states.
  • Key prop importance? — Helps React's reconciliation match old/new nodes correctly; never use index for reorderable lists.
  • How to optimise a slow React app? — Profiler → memo + useCallback + useMemo → split Context → useTransition → React Query → code splitting with Suspense.
